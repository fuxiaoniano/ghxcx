# 项目升级影响分析报告

**项目：** 口腔挂号小程序企业官方升级

**审计日期：** 2026-08-22

**审计范围：** 小程序前端、NestJS 后端、Prisma/MySQL 数据结构、Vue 管理后台、通知与公众号链路

**阶段结论：** 可以采用“新增模块 + 旧接口冻结 + 单表统一业务类型 + 可回滚 migration”的方式升级，无需重建登录、用户或管理后台。

## 1. 审计边界与基线

- 仓库是 pnpm monorepo，包含原生微信小程序、NestJS + Prisma 后端、Vue 3 + Element Plus 管理后台。
- Git 当前分支为 `main`，远端为 `https://github.com/fuxiaoniano/ghxcx.git`，审计开始时工作区无未提交改动。
- 当前仓库未提供可连接的本地/生产 `.env`，也没有可用 Docker 命令；本报告的数据库结论来自 `schema.prisma` 和 4 组历史 migration。上线前必须再对生产库执行只读结构、行数、索引和孤儿数据核验。
- 基线检查通过：后端 `tsc --noEmit`、后台 `vue-tsc --noEmit`、小程序 `tsc --noEmit` 均通过；后端 7 个测试套件、19 个测试全部通过。

## 2. 当前已有功能

### 2.1 小程序

- 现有页面仅 3 个：旧挂号落地页、挂号成功/详情页、我的挂号列表页。
- 旧挂号支持微信登录、手机号快捷授权与手工手机号、门店选择、姓名/年龄/缺牙情况/备注、隐私勾选、订阅消息、来源参数追踪。
- 当前没有 `tabBar`，没有企业首页、医生、套餐或新版个人中心。

### 2.2 用户与微信体系

- `users` 保存统一用户资料，手机号采用加密正文、HMAC 检索 hash、脱敏展示三份数据。
- `wechat_identities` 同时承载小程序 OpenID、公众号 OpenID、UnionID 和公众号关注状态，可复用来判断客服/公众号能力前置条件。
- 小程序现有登录及绑定接口：`POST /api/wechat/mini/login`、`/phone`、`/manual-phone`、`/bind-official-account`。

### 2.3 旧挂号业务

- 旧入口 `POST /api/appointments` 写入 `appointments`。
- 创建时复用当前用户手机号，使用 Redis 30 秒防重复提交，更新用户姓名/年龄，生成 `GH` 预约编号。
- 创建后异步转发院内回访系统，同时发送用户成功通知和工作人员新预约通知。
- 用户可通过 `GET /api/appointments/my` 与 `/my/:id` 查询自己的记录。

### 2.4 管理后台

- 现有同一后台已包含：仪表盘、挂号管理、用户管理、通知记录、系统配置、公众号菜单、公众号自动回复、回访接口、成员与通知、审计日志。
- 挂号管理已有分页、状态流转、备注、分配、手机号审计查看、通知重发、回访重发和 CSV 导出基础能力。
- 门店已在系统配置内管理；图片上传已有落地页资产上传实现，可抽取为通用医疗内容图片上传能力。
- 管理员体系为 `SUPER_ADMIN / MANAGER / STAFF` + `permissionsJson` 字符串数组；超级管理员自动放行，其他账号按装饰器权限校验。

### 2.5 数据库现状

现有表：`users`、`wechat_identities`、`appointments`、`notification_logs`、`admin_users`、`admin_wechat_invites`、`audit_logs`、`system_configs`、`clinics`。历史 migration 只做新增/兼容修改，没有删除核心业务表。

## 3. 可以复用的模块

| 能力 | 复用方式 |
| --- | --- |
| 小程序登录 | 所有新增需登录页面继续使用 Mini JWT 与 `MiniAuthGuard` |
| 用户与手机号 | 新预约/套餐申请只引用现有 `userId`，联系电话继续从加密用户资料复制，不新建客户表 |
| 公众号身份 | 使用 `wechat_identities.subscribedOfficialAccount` 判断关注状态，并沿用 OAuth/UnionID 绑定 |
| 管理员与权限 | 在现有权限数组增加 4 个权限，不新增后台账号体系 |
| 挂号统一管理 | 新业务仍写 `appointments`，通过 `type` 区分，原列表增加筛选与字段列 |
| 门店/医院 | 医生、出诊和预约引用现有 `clinics`，不重复维护医院名称 |
| 通知与回访 | 新预约创建后复用通知日志、员工通知和回访转发；根据业务类型生成不同文案 |
| 审计日志 | 所有后台新增/修改/删除、排序、状态切换继续写 `audit_logs` |
| 系统配置 | 医院品牌、客服路径、协议链接等低频配置继续放 `system_configs` |
| 图片上传 | 将现有 landing 图片上传实现抽取为通用上传服务，并保持旧 URL 可用 |

## 4. 需要新增的业务模块

### 4.1 后端

- 首页内容：轮播、广告、首页配置与推荐医生聚合接口。
- 科室与项目：科室 CRUD、项目 CRUD、排序、启停；项目点击进入新版预约。
- 医生：列表（按筛选一次返回全部，不分页）、详情、推荐、排期、图片与科室关联。
- 新版预约：科室项目选择、医生选择、日期时段、表单提交、成功详情；使用新接口，不改变旧 DTO。
- 套餐：分类、列表、详情、多图排序和套餐咨询申请。
- 个人中心：按业务类型返回挂号/预约/套餐申请记录，保留旧“我的挂号”接口。
- 通用上传：限制 MIME、扩展名、大小和目录，返回 HTTPS URL；删除资源前检查引用。

### 4.2 原管理后台扩展

- 首页管理：轮播图、广告、首页配置。
- 医生管理：医生、推荐、排期和图片。
- 科室管理：科室和科室项目。
- 套餐管理：分类、套餐与详情图排序。
- 原挂号管理：增加业务类型、医生、预约日期/时段筛选和展示；套餐申请仍进入此列表。

### 4.3 小程序新增页面

- 五栏导航：首页、医生介绍、预约挂号、推荐套餐、个人中心。
- 非 tabBar 页面：医生详情、预约步骤/表单/成功、套餐详情/申请、各类记录、协议页面。
- 医生列表按最新要求不分页；支持科室筛选，筛选结果全部展示。

## 5. 数据库升级设计建议

### 5.1 新表

| 表 | 关键字段与关系 |
| --- | --- |
| `home_banners` | 需求字段全部保留；补充索引 `status, sort` |
| `home_ads` | 需求字段全部保留；补充 `createdAt/updatedAt` 便于审计 |
| `dental_categories` | 作为科室主表；需求字段全部保留，补充时间字段 |
| `dental_projects` | 必需补充表：`categoryId/name/description/sort/status/createdAt/updatedAt`，承载科室右侧项目 |
| `doctors` | 需求字段全部保留；`departmentId` 外键指向 `dental_categories`；建议补 `clinicId` 复用医院表 |
| `doctor_schedules` | `doctorId/clinicId/date/timeSlot/status/capacity/bookedCount/sort/createdAt/updatedAt` |
| `package_categories` | `id/name/icon/sort/status/createdAt/updatedAt` |
| `packages` | 需求字段全部保留；价格使用 `Decimal(10,2)`，外键指向套餐分类 |
| `package_images` | 需求字段全部保留；增加唯一排序/普通索引及时间字段 |

说明：需求同时要求“科室 + 科室项目”后台管理，但原始表清单只给出 `dental_categories`，不足以表达一对多项目，因此必须新增 `dental_projects`。医生展示医院应复用 `clinics`，不能再维护一份自由文本医院数据。

### 5.2 `appointments` 增量字段

- 需求字段：`type`、`doctorId`、`appointmentDate`、`appointmentTime`、`symptomDescription`、`gender`。
- 为完整保存选择链路，建议增加：`dentalCategoryId`、`dentalProjectId`、`packageId`。
- `type` 设为非空且默认 `LEGACY_REGISTRATION`，migration 先加默认值并回填所有旧数据，确保旧查询与旧记录正常。
- 其他新增字段全部允许空值；旧挂号无需提供医生、日期、时段或套餐。
- 最新需求中姓名、性别未标“必填”。为不把现有 `appointments.name` 改成 nullable，新接口在未填写姓名时使用现有用户姓名，仍为空则存“未填写”；旧接口继续强制姓名必填。性别保持可空。
- 新业务联系电话仍必须来自现有已授权/手工绑定手机号，不新增明文电话列。

### 5.3 索引与删除策略

- `appointments` 增加 `type`、`doctorId`、`packageId`、`appointmentDate` 及常用组合索引。
- 内容表后台“删除”默认采用状态禁用/软删除语义；已被预约引用的医生、项目、套餐禁止物理删除。
- 仅未被引用的内容允许物理删除，且必须写审计日志。

### 5.4 回滚

- Prisma 本身不生成 down migration，因此每个升级 migration 同目录提供人工审核的 `rollback.sql`。
- 回滚顺序：先删除新增外键/索引和 `appointments` 新字段，再按依赖反序删除新表。
- 回滚前必须导出所有 `type != LEGACY_REGISTRATION` 的新业务数据；生产回滚不自动执行破坏性 SQL。

## 6. 冻结兼容面：不能覆盖或破坏的文件/语义

以下文件允许“外围调用或最小增量适配”，禁止重写、删除或改变现有请求/响应语义：

- `miniprogram/miniprogram/pages/landing/*`：旧挂号落地页继续可访问。
- `miniprogram/miniprogram/pages/success/*`：旧挂号成功与详情展示继续可用。
- `miniprogram/miniprogram/pages/appointments/*`：旧“我的挂号”列表继续可用。
- `server/src/modules/appointments/dto.ts` 中 `CreateAppointmentDto`：字段校验和必填语义保持。
- `POST /api/appointments` 现有控制器入口及 `AppointmentsService.create` 的手机号、防重、通知、回访语义保持。
- `GET /api/appointments/my`、`GET /api/appointments/my/:id` 的旧字段保持，只允许追加可选字段。
- `server/src/modules/auth/*`、`wechat-mini/*` 的 token/用户绑定行为保持。
- `notifications` 与 `followup-forwarder` 的旧挂号 payload 字段保持；新业务只追加字段。
- 现有 Prisma 表和列不得删除或重命名；`appointmentNo`、加密手机号三字段及状态枚举不可改变语义。
- 后台现有路由、菜单和旧挂号操作接口不得删除；新增菜单在同一 `Layout.vue` 和同一 `/api/admin` 鉴权域内扩展。

`miniprogram/miniprogram/app.json` 必须增量修改以注册新页面与五栏 tabBar，但旧 3 个页面仍保留在 pages 清单中，旧外部深链继续有效。

## 7. 必须兼容的接口

### 小程序/公众号

- `POST /api/wechat/mini/login`
- `POST /api/wechat/mini/phone`
- `POST /api/wechat/mini/manual-phone`
- `POST /api/wechat/mini/bind-official-account`
- `POST /api/appointments`
- `GET /api/appointments/my`
- `GET /api/appointments/my/:id`
- `GET /api/config/landing-page`
- `/wechat/oa/callback`、`/wechat/oa/oauth` 及回调路径

### 管理后台

- `/api/admin/appointments*` 的列表、详情、手机号查看、状态、备注、分配、通知/回访重试和导出。
- `/api/admin/users*`、`/notification-logs`、`/audit-logs`、`/configs`、`/clinics`。
- `/api/admin/official-account/*`、`/admin-users*`、`/appointment-notify`、`/followup-forward`。

兼容策略：旧接口不增加新的必填请求字段；响应只追加可选字段；CSV 在原列后追加新列；外部回访 payload 仅追加 `type` 等字段，不删除或改名。

## 8. 权限升级

- 新增：`HOME_MANAGE`、`DOCTOR_MANAGE`、`PACKAGE_MANAGE`、`APPOINTMENT_MANAGE`。
- 兼容现有 `MANAGE_APPOINTMENTS`：迁移期管理新版预约写操作接受 `APPOINTMENT_MANAGE`；超级管理员继续自动放行。旧挂号写操作继续使用原权限，避免已有成员突然失权。
- seed 只给超级管理员补齐新权限，不覆盖生产中其他管理员已有权限数组。

## 9. 参考图落地约束

- 采用医疗蓝、白色卡片、浅蓝灰背景和克制圆角阴影。
- 首页参考医院品牌头图、快捷入口、科室网格、广告和推荐医生；医生参考卡片列表与出诊详情；预约/套餐采用左分类右内容；个人中心采用头部身份卡 + 分组入口。
- 参考图中的“立即购买”在本项目统一改为“提交申请/立即咨询”，不接支付，不制造已成交语义。
- 医疗内容不使用夸大疗效、绝对化承诺或诊断性文案；价格与销售人数均由后台数据驱动。

## 10. 分阶段实施与门禁

1. 本报告确认并提交。
2. 新增 schema、forward migration、`rollback.sql` 和 migration 静态验证；不接页面。
3. 新增后端模块与契约测试；旧挂号测试必须继续通过。
4. 在原后台增加菜单、CRUD、筛选、审计与权限；不建立第二后台。
5. 新增小程序页面和 tabBar；旧页面保留并回归深链。
6. 联调验证医生自动选择、统一列表、套餐申请、图片排序、个人中心与客服关注提示。
7. 生产升级前进行备份、只读数据库核验、灰度发布和回滚演练。

## 11. 主要风险

- **生产库未知：** 当前无法核验生产数据规模、字符集、MySQL 小版本和异常数据，migration 上线前必须预演。
- **公众号客服能力限制：** 小程序能否直接打开公众号客服取决于主体、关联关系、微信开放能力和用户关注状态；需要真实 AppID、已关联公众号和真机验证，模拟器通过不等于上线可用。
- **五栏 tabBar 改动：** 会改变默认入口视觉，但旧页面路径必须继续保留以兼容公众号菜单、二维码和历史链接。
- **图片存储：** 当前是本地磁盘上传；若生产容器无持久卷或多实例部署，需先确认共享对象存储/持久卷方案。
- **业务命名：** 套餐不支付，后台与用户端统一称“套餐申请/咨询”，避免“购买记录”与真实支付混淆。

## 12. 第一阶段验收结论

现有架构具备增量升级条件。推荐方案不会复制登录、用户或后台，不会替换旧挂号接口；新业务通过独立 API 和新表扩展，最终统一写入 `appointments` 并通过 `type` 管理。进入 migration 实施前，应以本报告的冻结兼容面为回归基线。
